## 2. Fitur Baru: Audit Trail

Setiap dokumen bisnis sekarang mencatat **siapa** yang membuat, menyetujui, dan menyelesaikannya. Field ini **selalu diambil dari sisi backend** (dari `X-User-Id`, lihat bagian 4) — tidak pernah bisa diisi manual lewat body request.

### Tabel & kolom yang ditambahkan

| Tabel | Kolom baru |
|---|---|
| `warehouses` | `created_by` |
| `items` | `created_by` |
| `contacts` | `created_by` |
| `inventory_transactions` (inbound & outbound) | `created_by`, `completed_by` |
| `stock_transfers` | `created_by`, `approved_by`, `completed_by` |
| `stock_opnames` | `created_by`, `approved_by` |
| `invoices` (sales & purchase) | `created_by`, `completed_by` |
| `item_returns` | `created_by`, `approved_by`, `completed_by` |
| `payments` | `created_by` |

Semua kolom bertipe `INT NULL`, **tanpa foreign key** — karena tabel `users` berada di backend auth terpisah, bukan di database ini. Nilainya berupa ID user mentah saja.

### Perilaku khusus: transaksi turunan

Beberapa dokumen otomatis membuat dokumen lain saat di-complete (lihat [api-documentation.md](api-documentation.md) bagian Sales & Returns). Dokumen turunan ini **ikut diatribusikan ke user yang sama**:

- Sale di-complete oleh user X → OUTBOUND yang otomatis dibuat juga mencatat `created_by: X`, `completed_by: X`.
- Purchase di-complete oleh user X → INBOUND turunan juga `created_by: X`, `completed_by: X`.
- Return (GOOD + REPLACE) di-complete oleh user X → OUTBOUND replacement juga `created_by: X`, `completed_by: X`.

## 3. Fitur Baru: Activity Log

Tabel `activity_logs` baru, diisi **otomatis** oleh satu hook global — tidak bergantung pada modul mana yang dipanggil, jadi cakupannya penuh untuk semua endpoint mutating (`POST`/`PUT`/`DELETE`) yang sukses (status code `< 400`).

### Endpoint baru

| Method | Path | Keterangan |
|---|---|---|
| GET | `/api/activity-logs?user_id=&warehouse_id=&entity_type=&entity_id=&action=&from=&to=` | List, semua filter opsional, paginated |
| GET | `/api/activity-logs/:id` | Detail satu entri |

### Bentuk data

```json
{
  "id": 10,
  "user_id": 8,
  "warehouse_id": null,
  "action": "COMPLETE",
  "entity_type": "STOCK_TRANSFER",
  "entity_id": 7,
  "method": "POST",
  "endpoint": "/api/stock-transfers/7/complete",
  "status_code": 200,
  "metadata": null,
  "created_at": "2026-08-28 00:02:24.989"
}
```

`action` diturunkan otomatis dari path: `CREATE` (POST tanpa sub-path), `UPDATE` (PUT), `DELETE` (DELETE), atau nama sub-aksi dalam huruf besar (`COMPLETE`, `APPROVE`, `REJECT`, `CANCEL`, `SUBMIT`). `entity_type` mengikuti nama resource (`WAREHOUSE`, `ITEM`, `SALE`, `RETURN`, dst).

**Penting:** kegagalan menulis activity log **tidak pernah** menggagalkan request API yang sebenarnya — kalau insert log error, hanya dicatat di server log, response ke client tetap sukses normal.

## 4. Fitur Baru: User Context Header (Sementara)

Karena autentikasi/otorisasi sedang dibangun di backend terpisah, backend ini untuk sementara membaca identitas user dari header berikut (semuanya **opsional** — kalau tidak dikirim, kolom audit & activity log tersimpan `null`):

```
X-User-Id: 5
X-User-Role: admin-gudang
X-Warehouse-Id: 2
```

Ini **bukan** mekanisme keamanan — siapa pun bisa mengisi header ini dengan nilai apa saja. Header ini murni jembatan sementara supaya kolom audit sudah bisa terisi sebelum integrasi JWT dari backend auth selesai. Setelah integrasi JWT nanti, cara pengiriman identitas kemungkinan berubah (via `Authorization: Bearer <token>`), dan dokumentasi ini akan diperbarui.

## 5. Perubahan: Outbound Tidak Lagi Menerima `unit_price`

**Endpoint terdampak:** `POST /api/outbounds`, `PUT /api/outbounds/:id`, dan seluruh response `GET` yang menyertakan detail outbound.

### Sebelum
```json
{ "item_id": 1, "quantity": 5, "unit_price": 50000 }
```

### Sesudah
```json
{ "item_id": 1, "quantity": 5 }
```

Mengirim `unit_price` pada body outbound sekarang menghasilkan `400 VALIDATION_ERROR` (field dianggap tidak dikenal karena `additionalProperties: false`). Response detail outbound juga tidak lagi memiliki `unit_price`/`total_price`.

**Alasan:** biaya barang yang keluar via outbound selalu ditentukan oleh alokasi FIFO otomatis saat `complete`, bukan oleh input harga manual — field ini sebelumnya ada tapi tidak pernah dipakai dalam kalkulasi apa pun, jadi berpotensi menyesatkan. Lihat diskusi lebih lengkap di percakapan sebelumnya.

> Field ini masih dipakai **secara internal** oleh Sales (mencatat harga jual pada outbound otomatis) dan Returns (mencatat harga 0 pada outbound replacement) — perubahan ini hanya menutup akses publik ke field tersebut lewat endpoint `/api/outbounds`.

## 6. Detail Perubahan per Endpoint

Field baru yang muncul di response ditandai **+**. Tidak ada field lama yang dihapus kecuali disebutkan eksplisit di bagian 5.

| Endpoint | Field baru di response |
|---|---|
| `POST/PUT/GET /api/warehouses*` | **+** `created_by` |
| `POST/PUT/GET /api/items*` | **+** `created_by` |
| `POST/PUT/GET /api/contacts*` | **+** `created_by` |
| `POST/PUT/GET /api/inbounds*`, `POST /api/inbounds/:id/complete` | **+** `created_by`, **+** `completed_by` |
| `POST/PUT/GET /api/outbounds*`, `POST /api/outbounds/:id/complete` | **+** `created_by`, **+** `completed_by`; **−** `unit_price`, **−** `total_price` (di level detail) |
| `POST/PUT/GET /api/stock-transfers*`, `/approve`, `/complete` | **+** `created_by`, **+** `approved_by`, **+** `completed_by` |
| `POST/PUT/GET /api/stock-opnames*`, `/approve` | **+** `created_by`, **+** `approved_by` |
| `POST/PUT/GET /api/sales*`, `/complete` | **+** `created_by`, **+** `completed_by` |
| `POST/PUT/GET /api/purchases*`, `/complete` | **+** `created_by`, **+** `completed_by` |
| `GET /api/invoices*` | **+** `created_by`, **+** `completed_by` |
| `POST/GET /api/payments*`, `GET /api/invoices/:id/payments` | **+** `created_by` |
| `POST/PUT/GET /api/returns*`, `/approve`, `/complete` | **+** `created_by`, **+** `approved_by`, **+** `completed_by` |
| `GET /api/activity-logs`, `GET /api/activity-logs/:id` | **Endpoint baru sepenuhnya** |

Semua field audit bertipe `integer` atau `null` — tidak pernah string, tidak pernah wajib diisi di request manapun (selalu backend-derived).

## 8. Yang Perlu Diperhatikan Frontend

1. **Kirim `X-User-Id` di setiap request** (kalau sudah tahu siapa user yang login) supaya kolom audit & activity log terisi bermakna sejak sekarang — jangan tunggu integrasi JWT selesai.
2. **Hapus field `unit_price` dari form outbound manual** — lihat bagian 5. Kalau masih dikirim, request akan ditolak `400`.
3. **Field audit baru aman diabaikan** kalau UI belum siap menampilkannya — semuanya nullable dan tidak memengaruhi alur bisnis yang sudah ada.
4. Kalau butuh menampilkan "riwayat aktivitas" di UI (mis. di halaman detail dokumen), endpoint `GET /api/activity-logs?entity_type=SALE&entity_id=5` sudah siap dipakai.
